# Structure

## File layout

```
fluxion/
├── makefile    all of it: the calculator app (CEdev) by default, `make test` / `make web` / `make budget` for the PC side
├── icon.png
├── src/
│   ├── main.c  calculator start: app_run()
│   ├── main_pc.c  the same app on the PC (window, or scripted keys -> PNG)
│   ├── engine/   PineappleCAS engine (MIT, see its README for what's changed)
│   │   ├── cas/   simplify, expand, factor, derivative, identities, solve (+ trig families, systems in system.c), integrate, limit, truth (true / false statements), evalfn (floor, mod, conj ...), asym, approx (decimal), degrees. the show-the-work lines are steps.c with a file a kind: polysteps, systemsteps, ineqsteps, exprsteps (expand, factor, simplify), cmdsteps (tangent, critical, extrema, inflect, implicit)
│   │   ├── imath/  big-number + rational maths
│   │   └── pc/  PC-only command line + test runner (empty on the calculator)
│   ├── platform/  screen.h / keys.h / store.h: *_ti.c = graphx + keypadc + appvars, *_pc.c = framebuffer + SDL + files in build-pc/store. window_pc.c is the SDL window (resizable, Ctrl + / - / 0 zoom it in steps from 0.5 to 4), keys_pc.c turns the keyboard and the mouse into presses, clipboard.c is the system clipboard, web.c the browser build's keys and mouse
│   ├── render/
│   │   ├── layout.c    expression tree -> boxes with sizes + positions (no drawing)
│   │   ├── draw.c  boxes -> lines and text, through screen.h
│   │   └── fonts.c   bitmap fonts (generated by tools/bdf2c.py)
│   ├── editor/
│   │   └── editor.c    the input line: rows, templates, cursor; to engine string / boxes
│   ├── input/  the keypad side of input, the app only sees actions. input.h is what the app calls (wait for the next action, the modifier lights, how a command is typed here), actions.h is the list of actions
│   │   ├── keypad_input.c  waits for a key or a click and hands the app actions (a with the modifiers, plain without), no key codes. also the poll while the engine works
│   │   ├── bind.c  bind_ce.c / bind_nspire.c: which key does which action
│   │   └── sticky.c  [2nd] / [alpha] / [on]: tapped, on for the next key, a quick second tap locks it
│   └── ui/
│       ├── app.c    history, input line, running the engine
│       ├── areas.c  the top bar / body / soft-key bands, where the drawing gets its edges
│       ├── menu.c  the folder bar under the screen, the menus that open from it and the five keys a page draws on that bar, app.c just hands it hooks for picking, previews and the status line
│       ├── args.c  cutting a command's line at its commas and parsing the pieces, for every command file
│       ├── catalog.c  everything you can type or pick, and what the engine can do. its words are the name table too
│       ├── work.c  the show-the-work page, and calc1.c / polyfn.c / series.c / ineq.c the commands behind it (derivative at a point, tangent, apart, sum(, inequalities ...)
│       ├── page.c  full screen list pages (catalog, vars, mode)
│       ├── names.c  stored names and the typed-word lookup the editor asks
│       ├── vars.c   the [vars] page
│       ├── mode.c  the [mode] page
│       ├── settings.c  the angle mode, and saving the lot
│       └── theme.c  the colour presets, three colours each and the other two mixed from them, and the custom one worked out from a bg and an accent
├── test/
│   ├── pcas.tests   PineappleCAS's 256 engine tests
│   ├── fluxion.tests   Fluxion's engine tests (factor, solve, cancel, roots, forms)
│   ├── identity_masks.c   checks the identity skip is safe
│   ├── layout_dump.c   prints the box tree: ./build-pc/layout-dump '(X+1)^2/X'
│   ├── view.c  draws expressions: ./build-pc/view --png out.png 'X^2/2'
│   └── editor_test.c   editor steps -> picture: ./build-pc/editor-test t:2 frac t:1
└── docs/
```

only `src/platform/` is allowed to touch graphx, keypadc or SDL. everything else is the same code on the PC and the calculator, so i can test basically all of it on the PC without the emulator

## Testing

- PC: engine + layout built with `gcc`, takes a few seconds
- `make budget`: every test line's work (pcas_check calls), PC time and \*6500 for the CE, most work first. work is the same number on every machine, time per unit spreads ~4x (more on bignum heavy stuff)
- `python3 tools/fuzz.py [count] [seed] [pos|any] [mode]`: random expressions through `build-pc/fluxion`, checked at random points against sympy. modes are simplify (the default), expand, factor, derivative, integral, solve, limit, critical and system (2 equations, the sets have to satisfy both and match sympy's real ones). `any` tests negative letters too. a point where the input isn't real is skipped (Y^pi at a negative Y is noise), a point right next to a pole can show as wrong from the finite difference, simplify / expand / factor also report answers that are right but huge
- `python3 tools/golden.py seed count old-app new-app`: the same random key scripts through two `fluxion-app` builds, which PNGs differ. for refactors that must not change a pixel (keep a copy of the old binary first)
- `python3 tools/uifuzz.py seed count [fluxion-app]`: random key and click scripts through `fluxion-app --png`, prints the ones that crash, time out or trip a sanitizer. an asan build finds the most
- `tools/uikeys.py`: the key / click tokens and pasted commands that uifuzz.py and golden.py both build their scripts from, so a new key goes in one place
- CEmu: by hand. `cemu-autotester` comes with CEdev if i ever want scripted key presses

## Gotchas

- CEmu + relative paths: `-s bin/FLUXION.8xp` silently does nothing if CEmu is already open from another folder. use the full path (VS Code configs use `${workspaceFolder}`)
- IntelliSense thinks `int` is 32-bit, it's 24-bit on the eZ80. trust the compiler not the editor
- `make debug` right after a normal build says "nothing to be done", `make clean` first
- over 64 KB the toolchain splits it into a launcher + appvars (3 files to send), `COMPRESSED = YES` keeps it as one `.8xp`
- engine syntax: capital single letter variables, `_` is subtract, `-` is negate (TI style)
